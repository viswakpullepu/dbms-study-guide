Module 01

SQL Queries, Set Operations & Constraints

1.1 Basic SQL Query Structure

Data retrieval combines clauses in a strict logical order. The key exam distinction is when filtering happens: WHERE filters individual rows before grouping, whereas HAVING filters aggregated groups after GROUP BY. 

SELECT [DISTINCT] column1, column2
FROM table_name
WHERE row_condition
GROUP BY column1
HAVING group_condition
ORDER BY column1 ASC | DESC;
  • SELECT / DISTINCT: Picks columns and optionally removes duplicate rows.
  • JOIN: Combines rows across two or more tables using related columns.
  • Aggregates: COUNT(*), SUM(col), AVG(col), MIN(col), MAX(col) summarize groups into one value.

1.2 Pattern Matching with LIKE

The LIKE operator in a WHERE clause matches string patterns using two wildcards:

Wildcard Meaning Example Matches
% Zero, one, or many characters FirstName LIKE 'Ma%' Names starting with "Ma"
%...% Substring anywhere BookTitle LIKE '%life%' Titles containing "life"
_ Exactly one character Word LIKE 'h_l__' 5-letter words with 'h' at 1st and 'l' at 3rd
_ + % Combined fixed + variable length col LIKE 'A__o%' Starts with 'A', any 2 chars, then 'o'

1.3 Set Operators

All set operators require union compatibility: both SELECT statements must return the same number of columns, in the same order, with compatible data types.

Operator Behavior Duplicates
UNION Combines result sets of two queries Removed by default
UNION ALL Combines result sets without sorting/deduping Kept (faster)
INTERSECT Only rows present in both queries Removed
EXCEPT Rows in 1st query that are absent from 2nd Removed

Older MySQL workaround for EXCEPT: Use SELECT t1.id FROM t1 LEFT JOIN t2 ON t1.id = t2.id WHERE t2.id IS NULL;

1.4 Complex Integrity Constraints

  • CHECK Constraint: Enforces value ranges or patterns, e.g. Age INT CHECK (Age >= 18 AND Age <= 30) or Email LIKE '%@%.%'.
  • Composite Keys: Apply uniqueness or referential integrity across multiple columns: PRIMARY KEY (OrderID, ProductID) paired with separate FOREIGN KEY rules.
  • Stored Procedures: Reusable procedural blocks invoked explicitly to validate complex multi-step rules before writes.
  • Triggers: Procedural code that executes automatically in response to INSERT, UPDATE, or DELETE events on a table or view.
Module 02

Schema Refinement, Functional Dependencies & Decomposition

2.1 Redundancy and the 3 Data Anomalies

Storing repeated customer attributes inside an unnormalized Orders(OrderID, CustomerName, Product, CustomerAddress) table wastes disk space, slows updates, risks integrity, and causes three classic anomalies:

Update Anomaly

Changing Madhu's address requires editing every order row for Madhu. Missing one row leaves contradictory data.

Insertion Anomaly

Inserting a new order forces repeating the customer's name and address again (and a customer cannot be recorded without an order).

Deletion Anomaly

Deleting an order row can accidentally erase the customer's address if it was their only order in the table.

Solution: Decompose into Customers(CustomerID, CustomerName, CustomerAddress) and Orders(OrderID, CustomerID, Product).

2.2 Functional Dependencies (FDs) and Closure

A functional dependency X -> Y holds on relation R if whenever two tuples agree on X, they must also agree on Y (e.g., sid -> sname, zipcode -> cityname).

FD Concept Rule Example
Trivial FD Y is a subset of X (always holds) AB -> A, ABC -> AC
Full Functional Dependency Y depends on X and on no proper subset of X (StudentID, CourseID) -> Instructor
Transitive Dependency If A -> B and B -> C, then C depends transitively on A EmployeeID -> Department -> DepartmentLocation
Attribute Closure (X+) Set of all attributes functionally determined by X Given {A -> B, B -> C}, A+ = {A, B, C}

Superkey test: Compute X+. If X+ contains every attribute of relation R, then X is a superkey of R.

2.3 Lossless vs. Lossy Decomposition

Decomposition splits a relation R into sub-relations R1, R2. Every valid decomposition should aim for three properties:

  • Lossless Join (Mandatory): Joining R1 and R2 reconstructs the exact original relation R with zero missing rows and zero extra (spurious) rows. Test: (R1 ∩ R2) -> R1 or (R1 ∩ R2) -> R2 must hold.
  • Lossy Join (Avoid): When the common attribute is not a key of either sub-relation, the natural join creates false spurious tuples that were never in the original table.
  • Dependency Preservation: Every functional dependency can be checked within a single decomposed table without running a cross-table join.
  • Lack of Data Redundancy: Duplicate attributes are minimized across sub-relations.
Module 03

External Storage, File Organizations & Indexing

3.1 Storage System Hierarchy

Ordered from fastest and costliest per byte to slowest and largest capacity:

  1. Primary Storage (Volatile): CPU Registers, Cache (L1/L2/L3), Main Memory (RAM).
  2. Secondary Storage (Non-volatile): Flash Storage (SSDs, no moving parts) and Magnetic Disks (HDDs: tracks, sectors, cylinders).
  3. Tertiary / Off-line Storage: Optical Disks (CD/DVD/Blu-Ray) and Magnetic Tapes (sequential access for backups and archival).
  4. Quaternary Storage: Remote / Cloud Storage accessed over networks.

3.2 File Organizations and ISAM

Method Mechanism Strength Weakness
Sequential Sorted by key in contiguous storage Fast batch processing; simple Slow random lookup; shifting cost on mid-file insert/delete
Direct / Hashed Hash function maps key to bucket address O(1) equality search; uniform spread Poor for range queries; collisions and expensive rehashing
Indexed Primary data file + auxiliary key-pointer file Fast random and range searches Extra disk space; index maintenance overhead on writes
ISAM Sorted Data File + static Index File + Overflow Area Supports both sequential and direct access (~2 disk I/Os) Overflow area fills up; requires periodic reorganization

3.3 Indexing Taxonomy and Diagrams

An index entry pairs a Search Key with a Data Reference (block/record pointer).

Dense vs. Sparse Primary Index (2 records per block)

  • Clustered vs. Non-Clustered: A Clustered Index dictates the physical storage order of rows on disk (max 1 per table; great for range scans; slows inserts/updates). A Non-Clustered Index has logical order independent of physical order (multiple allowed per table; needs an extra lookup).
  • Multi-level, Bitmap, B+ Trees: Multi-level indexes index the index to reduce disk I/Os. Bitmap indexes use bit arrays for low-cardinality data warehouse columns. B+ trees keep balanced logarithmic height for disk access.

3.4 File Organization vs. Indexing vs. Performance Tuning

Dimension File Organization Indexing Performance Tuning
Granularity File level Table / column level Holistic (queries, indexes, caching, sharding, denormalization)
Resource Focus Disk space efficiency Disk + Memory CPU, Memory, Disk, and Network bandwidth
Query Impact Disk read/write speed Fast data retrieval Both read and write optimization
Complexity Straightforward Moderate to complex Highest (requires full system understanding)
Module 04

Transactions, Concurrency Control & Crash Recovery

4.1 ACID Properties and Transaction Lifecycle

Atomicity (all or nothing), Consistency (valid state to valid state), Isolation (concurrent execution matches serial outcome), and Durability (committed writes persist after crashes).

Transaction State Transition Diagram

4.2 Concurrency Conflicts, Serializability & Recoverability

Concurrent execution improves throughput and CPU utilization, but creates three conflicts if uncontrolled: Lost Update (W-W), Dirty Read (W-R on uncommitted data), and Unrepeatable Read (R-W changing values mid-transaction).

Conflict Serializability (Precedence Graph)

Two ops conflict if they belong to different transactions, access the same item, and at least one is a Write. Draw directed edge Ti -> Tj whenever Ti executes a conflicting op before Tj. No cycle = Conflict Serializable (topological order is the serial schedule).

View Serializability (3 Checks)

Two schedules are view equivalent if they have the same: (1) Initial Read, (2) Updated Read (reads-from source), and (3) Final Write on every data item.

  • Non-Recoverable Schedule: T2 reads uncommitted data from T1 and commits before T1. Forbidden.
  • Recoverable Schedule: If Tj reads from Ti, Ti must commit before Tj commits.
  • Cascading Rollback vs. Cascadeless: Reading uncommitted writes forces dependent transactions to abort if the writer fails. Cascadeless schedules allow reading only committed values.

4.3 Validation-Based Protocols (OCC) & Multiple Granularity

Optimistic Concurrency Control (OCC)

Assumes conflicts are rare (zero locks, deadlock-free):

  1. Read Phase: Read DB; buffer writes in local copies.
  2. Validation Phase: At commit time, verify no concurrent writer modified read/written items.
  3. Write Phase: Apply local updates if valid; else abort and restart.

Multiple Granularity Locking

Tree hierarchy: DB -> Table -> Page/Row -> Field. Ancestors hold intention locks:

  • IS: Descendants will get Shared (S) locks.
  • IX: Descendants will get Exclusive (X) locks.
  • SIX: Whole subtree locked in S + IX on some descendants (compatible only with IS).

4.4 Crash Recovery: Log-Based (WAL) vs. Shadow Paging

Technique How It Works On Commit / Crash
Log-Based (WAL) Records (TxnID, Item, OldVal, NewVal) to stable log before writing data pages to disk. Uses periodic Checkpoints. Restart Recovery: Analysis (find states) -> Redo committed txns (NewVal) -> Undo active txns (OldVal).
Shadow Paging Maintains Current and Shadow page tables. First page write makes a copy and updates only Current; Shadow points to clean pages. Commit: Discard Shadow table. Crash: Discard Current table and revert immediately to Shadow table.
